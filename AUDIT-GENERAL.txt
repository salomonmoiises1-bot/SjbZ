SB — Auditoría general única de arquitectura DSP

BASE
- Proyecto: SB / com.sb
- Backend objetivo: Android AudioEffect sobre sesión global 0
- DynamicsProcessing: API 28+
- AGP 8.2.2 / Kotlin 1.9.22 / compileSdk 34
- GitHub Actions: Gradle 8.5 + JDK 17

CRITERIO
La ruta de audio externo se audita como una aplicación system-wide: el audio de otras apps no se entrega como PCM a SB. Por eso la ruta real debe pasar por AudioEffect/DynamicsProcessing, igual que el enfoque system-wide documentado por Equalizer314. El pipeline PCM propio se conserva sólo para consumidores que realmente entreguen PCM al motor.

CORRECCIONES APLICADAS
1. DynamicsProcessing pasa a ser el backend principal del EQ, MBC y limiter cuando está disponible.
2. Equalizer nativo queda como fallback; no se ejecuta en paralelo con DynamicsProcessing para evitar doble ecualización.
3. SB mantiene sesión 0 como backend global. Las sesiones privadas anunciadas por Android se registran sólo para diagnóstico y no provocan que el motor salte de sesión.
4. DynamicsProcessing prueba primero hasta 32 bandas de Pre-EQ y reduce el número sólo si el HAL/vendor no acepta la configuración. El número físico aceptado se expone en capacidades.
5. Las 32/20/10 bandas lógicas se proyectan logarítmicamente sobre las bandas físicas reales del DP; no se afirma que el HAL tenga 32 filtros cuando no los tiene.
6. EQ, MDRC y limiter usan setters reales de DynamicsProcessing. Los cambios de crossover no reconstruyen el efecto: se actualizan directamente las bandas MBC, porque Android expone estos parámetros como modificables durante la ejecución.
7. EQ32 se actualiza mediante coalescing en un HandlerThread con separación mínima entre escrituras para evitar saturar el binder/audio HAL durante movimientos rápidos.
8. BassBoost y Virtualizer permanecen como efectos complementarios independientes. No se crean dos ecualizadores simultáneos.
9. Pre-Gain, Master Gain y Balance se aplican mediante las ganancias de entrada por canal disponibles en DynamicsProcessing. Esto mantiene los controles funcionales en la ruta AudioEffect; la API no ofrece un Master Gain/Balance separado posterior al limiter.
10. AutoGain deja de estimar un nivel ficticio a partir de los valores del EQ. Usa la medición RMS real del mix global mediante Visualizer cuando el dispositivo la admite, con límite y suavizado.
11. No se añadió RECORD_AUDIO, MediaProjection ni captura PCM de otras aplicaciones.
12. La persistencia de presets/configuración se mantiene, pero las escrituras durante arrastres de sliders se agrupan con un debounce de 180 ms para evitar escrituras DataStore por frame.
13. El coalescing del motor agrupa cambios de configuración rápidos antes de tocar el HAL.
14. El watchdog ya no considera sano un motor que no tenga ningún backend real disponible.
15. Headroom suma los boosts positivos que pueden coexistir para no subestimar el margen de seguridad.
16. DynamicsProcessing registra pérdida/recuperación de control mediante AudioEffect y el watchdog puede ejecutar auto-reclaim si otro efecto toma el control de la sesión 0.

RUTA FINAL
UI -> MainViewModel -> DspConfig.validate() -> DspEngine.updateConfig()
   -> DynamicsProcessingManager (principal)
      -> Pre-EQ lógico proyectado -> MBC 4 bandas -> Limiter
   -> BassBoostManager
   -> VirtualizerManager
   -> AudioMeterManager / Visualizer (medición RMS)

FALLBACK
Si DynamicsProcessing no puede crearse, EqualizerManager toma el EQ físico disponible y BassBoost/Virtualizer continúan como complementarios.

PCM DIRECTO
DspEngine.processPcm/processInterleaved y PcmAudioPipeline se conservan para uso directo con PCM proporcionado por un consumidor. No se conectan artificialmente al audio de YouTube/Spotify/TikTok porque SB no dispone de una fuente PCM de esas apps y el proyecto explícitamente no usa MediaProjection/RECORD_AUDIO.

VALIDACIÓN
- El ZIP mantiene el workflow que instala Gradle 8.5 directamente en GitHub Actions; no depende de gradle-wrapper.jar para el build de Actions.
- En este entorno local no se pudo ejecutar ./gradlew porque el ZIP no contiene gradle-wrapper.jar. Esto no equivale a un fallo del workflow: la acción usa gradle/actions/setup-gradle para instalar Gradle 8.5.
- Antes de considerar el APK validado, GitHub Actions debe completar test + assembleRelease y producir release-output/SB.apk.
